# Migrating from 8.x to 9.0

sqlane 9.0 renames the "job name" to the **lane**: the jobs that share a name, with the default options of its
definition. The lanes share the table and the workers of an instance, with fair sharing between them; a lane is not a
priority. The rename runs through the API, the code and the database. Nothing else changes: no new behavior, no new
method.

A lane is unrelated to the `lanes` option of 4.x, which became the local concurrency limits in 5.0, and `LaneOptions` is
unrelated to the 4.x type of that name, removed in 5.0.

## Upgrade

1. Stop every process of 8.x on the prefix.
2. Run `schema.migrate()` with 9.0. It applies `0009_lanes`, which renames the columns.
3. Deploy 9.0.

9.0 requires `0009_lanes`: `schema.getMigrationStatus()` lists it in `missingRequired` until it is applied. If your
migration tool pins the version of sqlane, add a migration file that pins `'9.0.0'`, with a down that goes back to
`'8.0.0'`:

```js
up: () => sqlane.schema.migrate({ targetVersion: '9.0.0' }),
down: () => sqlane.schema.rollback({ targetVersion: '8.0.0', lockTimeout: '10s' }),
```

The renames change only the metadata, but each takes the lock of its table: it waits for the open transactions on the
table, and the queries that come after it wait for it. Run `schema.migrate()` with no open transaction on the jobs
table. The code of 8.x does not run on the renamed columns, and the code of 9.0 does not run on the old ones.

## The rename

| 8.x                                                                    | 9.0                                        |
| ---------------------------------------------------------------------- | ------------------------------------------ |
| `defineJob(options)`                                                   | `defineLane(options)`                      |
| `JobDefinition`                                                        | `LaneDefinition`                           |
| `JobOptions`: the options of `defineLane`                              | `LaneOptions`                              |
| `failureJob`: definition, enqueue option, `JobRecord`, event field     | `failureLane`                              |
| `sqlane.handle(job, handler)`                                          | `sqlane.lanes.add(lane, handler)`          |
| `sqlane.jobs.stats()`                                                  | `sqlane.lanes.stats()`                     |
| `JobStats`                                                             | `LaneStats`, its entries still have `name` |
| —                                                                      | `SqlaneLanes`: the type of `sqlane.lanes`  |
| `createSqlane({ jobs })`                                               | `createSqlane({ lanes })`                  |
| `createSqlane({ unknownJobs })`                                        | `createSqlane({ unknownLanes })`           |
| `UnknownJobError`, code `UNKNOWN_JOB`                                  | `UnknownLaneError`, code `UNKNOWN_LANE`    |
| `jobName`: `JobFilter`, `JobSelector`, the events, the log fields      | `lane`                                     |
| `name`: `JobInfo`, `JobRecord`, `ScheduleInfo`, `FailedJobPayload.job` | `lane`                                     |
| The parameter `job` of `enqueue`, `enqueueMany` and `schedule`         | `lane`, at the same position               |

An object that is a lane names it `name`: `LaneDefinition.name`, `LaneStats.name`. An object that refers to a lane
names it `lane`. The messages of the errors say lane too: `lanes.add() after start()`, `"lanes" must be an array of
lane definitions`, `the lane is not in "lanes" and not added`.

`lanes.add` keeps the rules of `handle`: before `start()` and `drain()` only, and no options. It means that this process
runs the lane. `lanes.stats` keeps those of `jobs.stats`: every lane in the database, at any time.

The job ids do not change: `<lane>:<dedupeKey>` is the id of 8.x, so the jobs of 8.x keep deduplicating, and so do the
slots of the schedules. A failure job added by 9.0 gets `job.lane` in its payload, where one of 8.x has `job.name`: a
handler of a failure lane that may still get jobs of 8.x reads both.

These keep their names: the event type `failure_job_not_added`, `JobRecord`, `JobInfo`, `JobFilter`, `JobSelector`,
`JobDefaults`, `jobId` and `jobIds`, `scheduleId`, `sqlane.schedule()` and the other methods of `sqlane.jobs`.

The errors that pointed to the options of older majors are gone: `concurrency`, `maxConcurrency` and the `lanes` of
4.x, and `mutexKeys` of 5.x (in a definition and in the enqueue options), now reject as unknown or bad options, and so
does the enqueue option `jobId` of 7.x.

## The tables

`0009_lanes` renames the columns, and on MySQL and MariaDB an index:

| 8.x                                                    | 9.0                              |
| ------------------------------------------------------ | -------------------------------- |
| `sqlane_jobs.job_name`                                 | `sqlane_jobs.lane`               |
| `sqlane_jobs.failure_job`                              | `sqlane_jobs.failure_lane`       |
| `sqlane_schedules.job_name`                            | `sqlane_schedules.lane`          |
| MySQL, MariaDB: index `sqlane_jobs_status_name_run_at` | `sqlane_jobs_status_lane_run_at` |

Update the SQL of your own, the views and the ORM models of these tables. The other indexes keep their names.

On MySQL and MariaDB, `0009_lanes` also renames the index `sqlane_jobs_status_name_run_at`: if it was dropped or
renamed by hand, restore it before `schema.migrate()` (`schema.findSchemaProblems()` shows it).

## Rollback

Run `schema.rollback({ targetVersion: '8.0.0' })` with 9.0: it renames the columns back. Then deploy 8.x. As for the
upgrade, stop the processes of 9.0 first.
