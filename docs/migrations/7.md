# Migrating from 6.x to 7.0

sqlane 7.0 makes the database explicit. Every adapter takes `dialect`, and the first `start()` or `migrate()` checks
that the server is that database, at a supported version, with a supported `sql_mode` on MySQL and MariaDB. A
MariaDB server can no longer run the SQL of MySQL by mistake.

7.0 does not change the schema: there is no migration to run.

## Pass `dialect` to your adapter

The options argument is now required on every adapter, with `dialect`: `'postgres'`, `'mysql'` or `'mariadb'`. Without
it, the adapter throws a `ConfigError`, and TypeScript reports a missing argument.

| 6.x                                  | 7.0                                                      |
| ------------------------------------ | -------------------------------------------------------- |
| `mysql2Adapter(pool)`                | `mysql2Adapter(pool, { dialect: 'mysql' })`              |
| `pgAdapter(pool, { notify: true })`  | `pgAdapter(pool, { dialect: 'postgres', notify: true })` |
| `postgresJsAdapter(sql)`             | `postgresJsAdapter(sql, { dialect: 'postgres' })`        |
| `knexAdapter(knex)`                  | `knexAdapter(knex, { dialect: 'postgres' })`             |
| `drizzleAdapter(db)`                 | `drizzleAdapter(db, { dialect: 'postgres' })`            |
| `sequelizeAdapter(sequelize)`        | `sequelizeAdapter(sequelize, { dialect: 'postgres' })`   |
| `typeOrmAdapter(dataSource)`         | `typeOrmAdapter(dataSource, { dialect: 'postgres' })`    |
| `kyselyAdapter(db, { dialect })`     | Unchanged                                                |
| `prismaAdapter(prisma, { dialect })` | Unchanged                                                |
| `mikroOrmAdapter(em, { dialect })`   | Unchanged                                                |

On MySQL or MariaDB, pass `'mysql'` or `'mariadb'` instead of `'postgres'`. In 6.x, an adapter over mysql2 ran the SQL
of MySQL unless you passed `'mariadb'`; in 7.0 there is no default.

Knex, Drizzle, Sequelize and TypeORM know their database, so a `dialect` that does not match it throws a `ConfigError`
when you create the adapter. The [dialect table](../adapters.md#the-dialect-and-the-server-check) lists the values
that each library accepts.

## The server check

The first `start()` or `migrate()` of an instance reads the server's version, and on MySQL and MariaDB its `sql_mode`.
A process that only enqueues never runs the check. Each failure is a `ConfigError` that says how to fix it:

| Failure                     | Example message                                                                                                                | Fix                                                                     |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------- |
| Another database            | `start(): "dialect" is "mysql", but the database is MariaDB 11.8.9: pass dialect: 'mariadb' to the adapter`                    | Pass the dialect that the message names                                 |
| A version below the minimum | `start(): MySQL 8.0.36 is below the supported minimum 8.4: upgrade it, or pass allowUnsupportedDbVersion: true to the adapter` | Upgrade, or pass `allowUnsupportedDbVersion: true`                      |
| An unsupported `sql_mode`   | `start(): the sql_mode of MySQL lacks STRICT_TRANS_TABLES or STRICT_ALL_TABLES, …`                                             | Make `sql_mode` strict, or pass `allowUnsupportedDbConfiguration: true` |
| `NO_BACKSLASH_ESCAPES`      | `start(): the sql_mode of MySQL has NO_BACKSLASH_ESCAPES: …`                                                                   | Remove the flag: no option allows it                                    |

The minimum versions are those of 6.x: PostgreSQL 15, MySQL 8.4, MariaDB 10.11. 6.x documented them; 7.0 enforces
them. With `allowUnsupportedDbVersion` or `allowUnsupportedDbConfiguration`, sqlane logs a warning through the `logger`
of `createSqlane` instead of throwing. sqlane is not tested in these setups.

### Amazon RDS and Aurora MySQL

The default DB parameter group of RDS MySQL sets `sql_mode` to `NO_ENGINE_SUBSTITUTION` only, which fails the check.
Set the `sql_mode` parameter of a custom parameter group to the default mode of MySQL 8.4:

```text
ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION
```

`sql_mode` applies to your app's queries too: in strict mode, MySQL rejects a value that it used to truncate with a
warning. If your app is not ready, pass `allowUnsupportedDbConfiguration: true` while you fix it. The
[`sql_mode` section](../adapters.md#the-dialect-and-the-server-check) lists the required flags.

## Upgrading a running system

7.0 reads and writes the same tables as 6.x, so 6.x and 7.0 processes can run together during a rolling deploy.

If the database is down when a 7.0 worker starts, `start()` resolves and emits an `error` event with the operation
`server_check`. The worker claims no job until the check passes.
