# Migrating from 5.x to 6.0

sqlane 6.0 replaces mutex keys and concurrency groups with concurrency limits. A limit is declared once, with
`defineConcurrencyLimit({ name, max })`, and a job definition lists it in one of two places:

- `localConcurrencyLimits`: each process counts its own jobs, in memory. This replaces `handle({ maxConcurrency })` and
  concurrency groups.
- `globalConcurrencyLimits`: the whole cluster counts the jobs of each key, in the database. This replaces mutex keys:
  a mutex key is a global limit with `max: 1`.

All the options of a job name are now in its definition: `handle()` takes no options. 6.0 changes the schema: run
`migrate()`, or apply `0005_concurrency_limits`, `0006_concurrency_slots` and `0007_rate_limits` with your migration
tool.

| 5.x                                                                     | 6.0                                                                                                        |
| ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `createSqlane({ maxConcurrency: 10 })`                                  | `createSqlane({ localMaxConcurrency: 10 })`                                                                |
| `defineConcurrencyGroup({ name: 'heavy', maxConcurrency: 2 })`          | `defineConcurrencyLimit({ name: 'heavy', max: 2 })`                                                        |
| `handle(x, fn, { concurrencyGroup: heavy })`                            | `defineJob({ name: 'x', localConcurrencyLimits: [heavy] })`, `handle(x, fn)`                               |
| `handle(x, fn, { maxConcurrency: 4 })`                                  | a limit of its own: `localConcurrencyLimits: [defineConcurrencyLimit({ name: 'x', max: 4 })]`              |
| `handle(x, fn, { fairShareWeight: 3, timeout: '5m' })`                  | `defineJob({ name: 'x', fairShareWeight: 3, timeout: '5m' })`                                              |
| One concurrency group per handler                                       | Any number of local limits per definition: a job starts while each of them has room                        |
| A cap above the instance's `maxConcurrency`: `ConfigError` at `start()` | Accepted: the lower one applies, so one definition fits large and small machines                           |
| ``mutexKeys: (payload) => [`order:${payload.orderId}`]``                | `globalConcurrencyLimits: ({ payload }) => [order.key(payload.orderId)]`, with `order` a limit of `max: 1` |
| `enqueue(…, { mutexKeys: ['order:1'] })`                                | `enqueue(…, { globalConcurrencyLimits: [order.key(1)] })`                                                  |
| `job.mutexKeys` in the handler: `['order:1']`                           | `job.globalConcurrencyLimits`: `[{ key: 'order:1', max: 1 }]`                                              |
| `InvalidMutexKeyError`, code `INVALID_MUTEX_KEY`                        | `InvalidConcurrencyLimitError`, code `INVALID_CONCURRENCY_LIMIT`                                           |
| `HandleOptions`, `ConcurrencyGroup`, `ConcurrencyGroupOptions` (types)  | `ConcurrencyLimit`, `ConcurrencyLimitOptions`, `ConcurrencyLimitKey`                                       |
| `getStats()`: `pending`                                                 | `pending` also counts the blocked jobs (see below)                                                         |

The old options throw a `ConfigError` (or an `InvalidOptionsError` at enqueue) that says what to use, so a missed
change fails at startup:

- `createSqlane: "maxConcurrency" is now "localMaxConcurrency" (6.0)`;
- `handle("x"): handle() takes no options since 6.0: set "timeout" and "fairShareWeight" in defineJob(), and replace
  "maxConcurrency" and "concurrencyGroup" with "localConcurrencyLimits"`;
- `defineJob("x"): "mutexKeys" was removed in 6.0: return a limit with max 1, or its keys, from
  "globalConcurrencyLimits"`;
- `enqueue("x"): "mutexKeys" was removed in 6.0: use "globalConcurrencyLimits"`.

## An example

5.x:

```js
export const heavy = defineConcurrencyGroup({ name: 'heavy', maxConcurrency: 2 });
export const syncOrder = defineJob({
    name: 'sync_order',
    mutexKeys: payload => [`order:${payload.orderId}`],
    timeout: '2m',
});

const sqlane = createSqlane({ adapter, maxConcurrency: 10 });

sqlane.handle(transcode, work, { concurrencyGroup: heavy, timeout: '5m' });
sqlane.handle(syncOrder, sync, { maxConcurrency: 4 });
sqlane.handle(sendEmail, send, { fairShareWeight: 3 });
```

6.0:

```js
import { createSqlane, defineConcurrencyLimit, defineJob } from '@sqlane/core';

export const heavy = defineConcurrencyLimit({ name: 'heavy', max: 2 }); // per process
export const order = defineConcurrencyLimit({ name: 'order', max: 1 }); // per key, in the whole cluster
export const orderSyncs = defineConcurrencyLimit({ name: 'order_syncs', max: 4 }); // per process

export const transcode = defineJob({ name: 'transcode', timeout: '5m', localConcurrencyLimits: [heavy] });
export const syncOrder = defineJob({
    name: 'sync_order',
    timeout: '2m',
    globalConcurrencyLimits: ({ payload }) => [order.key(payload.orderId)],
    localConcurrencyLimits: [orderSyncs],
});
export const sendEmail = defineJob({ name: 'send_email', fairShareWeight: 3 });

const sqlane = createSqlane({ adapter, localMaxConcurrency: 10 });

sqlane.handle(transcode, work);
sqlane.handle(syncOrder, sync);
sqlane.handle(sendEmail, send);
```

## Upgrading a running system

Stop every 5.x process before the first 6.0 process starts, and run the migrations in between. 5.x and 6.0 processes
must not run together: 5.x reads the tables that 6.0 removes.

The migrations keep the jobs of 5.x: a mutex key of a pending job becomes a key with `max: 1`, and a held key becomes
slot 0 of its key. The key of a job that was running when its process stopped stays held until the stall recovery
takes the job, as in 5.x. On MySQL and MariaDB, `0005_concurrency_limits`
is a single `ALTER TABLE` of `sqlane_jobs`: it locks the table while it copies it, which takes longer on a big table.

## What changes at runtime

- **A max above 1.** A key of a global limit with `max: 3` runs up to 3 jobs at once, in the whole cluster. A job
  starts while each of its keys has fewer running jobs than its max.
- **Blocked jobs.** A job whose key is full is `blocked` on it, out of the due jobs, until a job of the key ends. A
  flood of jobs on one key no longer holds back the other keys of its name: in 5.x, the search for startable jobs read
  the oldest 500 due jobs of a name, so 500 jobs waiting for one key stopped the others.
- **The order of a key.** Jobs of a key start in FIFO order among those that can start. A job with several keys waits
  only for its full keys, so under contention it can wait longer than a newer job with fewer keys. In 5.x, a job never
  passed an older job that shared one of its keys.
- **Maxes are frozen at enqueue**, with the keys, as `maxAttempts` is. A deploy that changes a max applies to the jobs
  enqueued after it.
- **Local limits** replace concurrency groups in fair share: a name at any of its local limits takes no slot.
- **Performance.** An enqueue writes one row fewer per key (the table `sqlane_job_keys` is gone). The end of a job with
  global limits runs one more statement, which makes the blocked jobs of its keys due.
