# Migrating from 7.x to 8.0

sqlane 8.0 moves the schema to `sqlane.schema`. Each migration is tagged with the version of sqlane that ships it, so
your own migration tool can pin a version, go back with a rollback, or drop the tables. Two reads tell whether the
schema is ready.

It also moves the stats to `sqlane.jobs.stats()`, where the blocked jobs leave `pending` for a field of their own; moves
the list of schedules to `sqlane.schedules.list()`; and renames the enqueue option `jobId` to `dedupeKey`.

8.0 does not change the schema, but it makes `0008_job_list` (7.1.0) required: `schema.getMigrationStatus()` lists it
in `missingRequired` until it is applied. A database of 7.0.x lacks it, so run `schema.migrate()` before or during the
upgrade.

## `migrate()` is now `schema.migrate()`

| 7.x                               | 8.0                                      |
| --------------------------------- | ---------------------------------------- |
| `sqlane.migrate()`                | `sqlane.schema.migrate()`                |
| `sqlane.migrate({ lockTimeout })` | `sqlane.schema.migrate({ lockTimeout })` |
| `getMigrations({ dialect })`      | Removed: see below                       |
| The `Migration` type              | Removed                                  |

The error messages name the new method: `schema.migrate(): …`, and
`start(): the table sqlane_schedules is missing: run schema.migrate()`.

New in 8.0:

- `schema.migrate({ targetVersion })` applies only the migrations tagged at or below a version.
- `schema.rollback({ targetVersion })` reverts the migrations tagged above a version.
- `schema.drop()` drops the tables of sqlane.
- `schema.getMigrationStatus()` and `schema.findSchemaProblems()` check the schema, before `start()` or in a readiness
  probe.

The [API reference](../api.md#sqlaneschemamigrate) describes them, with a full migration file of Sequelize.

## `getMigrations()` is removed

8.0 has no other way to get the SQL. If your migration tool applied the statements of `getMigrations()`, call
`schema.migrate()` from a migration file instead, with the version that the file pins:

```js
up: () => sqlane.schema.migrate({ targetVersion: '8.0.0' }),
down: () => sqlane.schema.drop(),
```

`schema.migrate()` reads the ids that `sqlane_migrations` records. If your tool applied the statements without
recording the ids there, `schema.migrate()` runs them again and fails at the migration of the job keys, which reads the
column `mutex_keys` that 6.0 renamed: `0003_job_keys` on PostgreSQL, `0002_job_keys` on MySQL and MariaDB. On
PostgreSQL the failed run changes nothing. On MySQL and MariaDB, it has already recorded `0001_initial` and created an
empty `sqlane_job_keys` and `sqlane_mutexes` again. Pick one of two ways:

- Drop the tables of sqlane and run `schema.migrate()` again. The jobs in them are lost.
- Record the ids by hand:
    1. On PostgreSQL, the failed run rolled back: create the table.

        ```sql
        CREATE TABLE sqlane_migrations (
            id varchar(64) COLLATE "C" NOT NULL PRIMARY KEY,
            applied_at timestamptz(3) NOT NULL
        )
        ```

        On MySQL and MariaDB, delete its rows: the failed run recorded `0001_initial`.

    2. On MySQL and MariaDB, drop the empty `sqlane_job_keys` and `sqlane_mutexes`.
    3. Add one row per migration that your tool applied:
       `INSERT INTO sqlane_migrations (id, applied_at) VALUES ('<id>', now())` (`UTC_TIMESTAMP(3)` on MySQL and
       MariaDB).
    4. Run `schema.migrate()` again: it applies only what is missing.

The ids of each dialect:

| Dialect        | Ids                                                                                                                                                               |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL     | `0001_initial`, `0002_pending_order`, `0003_job_keys`, `0004_schedules`, `0005_concurrency_limits`, `0006_concurrency_slots`, `0007_rate_limits`, `0008_job_list` |
| MySQL, MariaDB | `0001_initial`, `0002_job_keys`, `0004_schedules`, `0005_concurrency_limits`, `0006_concurrency_slots`, `0007_rate_limits`, `0008_job_list`                       |

Then check the result: `schema.findSchemaProblems()` resolves to `{ ok: true, problems: [] }`.

## `getStats()` is now `jobs.stats()`

| 7.x                                   | 8.0                                                    |
| ------------------------------------- | ------------------------------------------------------ |
| `sqlane.getStats()`                   | `sqlane.jobs.stats()`                                  |
| `pending`: waiting and blocked        | `pending`: waiting, not blocked; add `blocked` for 7.x |
| No count of the blocked jobs          | `blocked`: the jobs blocked on a key of a global limit |
| No count of the completed jobs        | `completed`: the completed jobs that sqlane keeps      |
| A name with only completed jobs: none | A name with only completed jobs: an entry              |

`due` and `oldestDueAgeMs` do not change: they never counted the blocked jobs. An alert on `pending` that meant "jobs
wait" now needs `pending + blocked`.

`jobs.stats()` reads every row kept, on every dialect, as `getStats()` did in 7.x: its cost does not change. Only the
count of the completed jobs is new.

## `getSchedules()` is now `schedules.list()`

| 7.x                     | 8.0                       |
| ----------------------- | ------------------------- |
| `sqlane.getSchedules()` | `sqlane.schedules.list()` |

The result does not change. `sqlane.schedule()` stays.

## The enqueue option `jobId` is now `dedupeKey`

| 7.x                                              | 8.0                                                  |
| ------------------------------------------------ | ---------------------------------------------------- |
| `enqueue(db, job, payload, { jobId })`           | `enqueue(db, job, payload, { dedupeKey })`           |
| `enqueueMany(db, job, [{ options: { jobId } }])` | `enqueueMany(db, job, [{ options: { dedupeKey } }])` |
| `EnqueueOptions.jobId`                           | `EnqueueOptions.dedupeKey`                           |

The rules do not change: 1 to 120 printable ASCII characters, without spaces at the ends, not starting with
`schedule:`. The job id is still `<job name>:<dedupeKey>`, so the jobs of 7.x keep deduplicating. `jobId` rejects with
an `InvalidOptionsError`: `"jobId" was renamed in 8.0: use "dedupeKey"`, and the types reject it too. Elsewhere `jobId`
keeps its meaning, the full id of a job: in the events, `jobs.get(jobId)`, `jobIds` of the bulk methods.

The new type `SqlaneSchedules` is the type of `sqlane.schedules`; `JobStats` gains `blocked` and `completed`.

## Upgrading a running system

To a new major, sqlane's rule is to stop the processes of the old major, run `schema.migrate()`, then deploy
([Versions](../design.md#versions)). 8.0 is an exception: it changes no table, and reads and writes them as 7.x does.
Once `schema.migrate()` has run, 7.x and 8.0 processes can share a prefix during a rolling deploy. Only the calls
above change.
