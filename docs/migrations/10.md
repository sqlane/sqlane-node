# Migrating from 9.x to 10.0

sqlane 10.0 splits the API in two scopes. The **sqlane** (`createSqlane`) acts on the database, for every process: it
enqueues, reads and changes the jobs, the schedules and the tables. A **runner** (`createRunner(sqlane)`) acts on this
process: it mounts handlers and schedules, and runs them. A producer creates no runner. The lanes, the handlers and the
schedules are definitions: frozen values that a runner mounts. 10.0 also adds the **global pauses**: a lane or a
schedule paused in the database, for every process. It needs a new migration, `0010_pause`.

## Upgrade

1. Stop every process of 9.x on the prefix.
2. Run `schema.migrate()` with 10.0. It applies `0010_pause`.
3. Deploy 10.0.

`runner.start()` and `runner.drain()` reject with a `ConfigError` until `0010_pause` is applied (a database that is down
at `start()`: it resolves, emits an `error` event, and claims nothing until it can check). `schema.migrate()` does not
need it. `schema.getMigrationStatus()` lists it in `missingRequired` under 10.0. If your migration tool pins the version
of sqlane, add a migration file that pins `'10.0.0'`, with a down that goes back to `'9.0.0'`:

```js
up: () => sqlane.schema.migrate({ targetVersion: '10.0.0' }),
down: () => sqlane.schema.rollback({ targetVersion: '9.0.0', lockTimeout: '10s' }),
```

`0010_pause` creates a table and adds a nullable column to the table of the schedules: no row is written or copied. The
`ALTER TABLE` takes the lock of `sqlane_schedules`, as any DDL: run `schema.migrate()` with no open transaction on it.

## Definitions and the runner

```js
// 9.x
const sqlane = createSqlane({ adapter, lanes: [report], localMaxConcurrency: 20 });
sqlane.lanes.add(report, build);
sqlane.schedule(report, { cron: '0 6 * * *' });
await sqlane.start();

// 10.0
const nightly = defineSchedule(report, { key: 'nightly', cron: '0 6 * * *' }); // next to the lane
const sqlane = createSqlane({ adapter });
const runner = createRunner(sqlane, { localMaxConcurrency: 20 });
runner.mount([defineHandler(report, build), nightly]);
await runner.start();
```

| 9.x                                                                         | 10.0                                                        |
| --------------------------------------------------------------------------- | ----------------------------------------------------------- |
| `sqlane.lanes.add(lane, handler)`                                           | `runner.mount([defineHandler(lane, handler)])`              |
| `sqlane.schedule(lane, options)`                                            | `runner.mount([defineSchedule(lane, { key, ...options })])` |
| a keyless schedule, id `<lane>`                                             | a `key` is required: id `<lane>:<key>`                      |
| `enqueue(…, { slot })`                                                      | `sqlane.schedules.runSlot(schedule, { at })`                |
| `sqlane.start()`, `drain()`, `close()` (the worker)                         | `runner.start()`, `drain()`, `close()`                      |
| `sqlane.wake()`                                                             | none: the enqueues and the hints wake the runner            |
| `createSqlane({ localMaxConcurrency })`                                     | `createRunner(sqlane, { localMaxConcurrency, logger })`     |
| `createSqlane({ lanes, unknownLanes })`, `UnknownLaneError`, `UNKNOWN_LANE` | none: `enqueue` takes a lane definition                     |
| `enqueue`, `enqueueMany` and `failureLane` with a name                      | a lane definition only                                      |
| `defineLane({ localConcurrencyLimits, localRateLimits, fairShareWeight })`  | `defineHandler(lane, fn, { … })`: they are per process      |
| `EnqueueOptions.failureLane`, `JobRecord.failureLane`                       | none: the failure lane comes from the definition            |
| `ScheduleInfo.registered`                                                   | `runner.getStatus(schedule).mounted`                        |

A mount works before `start()` and after it: it claims and fires at once. `mount.unmount()` stops its lanes and its
schedules in this process; the jobs that run go on to their end. `sqlane.close()` closes the runner, then stops the
hint. The reads and the admin methods (`jobs.list`, `retry`, `cancel`, `remove`) still take a lane definition or a name.

New in the runner: `runner.pauseLocally(lane)` / `resumeLocally(lane)` (this process claims none of the jobs of the
lane, for the life of the runner) and `runner.getStatus(lane | schedule)`.

## Schedules: keys, and the rows of 9.x

A schedule needs a `key`: its id is `<lane>:<key>`, and the job id of a slot `<lane>:schedule:<key>:<ISO>`. A schedule
that had a key in 9.x keeps its id and its row. A keyless one gets a new id with its key: a new schedule, whose row
starts with its cursor at the first start of 10.0, so the slots before it do not run. The rows of the keyless schedules
of 9.x stay in the table, and `schedules.list()` lists them: delete each with `sqlane.schedules.remove('<lane>')`,
before or after `schema.migrate()`.

`schedules.list()` lists the rows of the table: a schedule is listed once a started runner has mounted it.

## Failure lanes and stalls

- A job that fails for good gets the failure job of its lane's definition **in the process that fails it**, no longer
  the `failureLane` stored at enqueue. The column `failure_lane` stays in the table, and the enqueue no longer writes it.
- After `maxStalls` stalls, the next stall puts the job back as any stall, and keeps its due time. Its next claim, in a
  process that handles its lane, fails it at once without its handler and without an attempt, with a `StalledError`
  and the failure job of that process's definition (events `claimed`, then `failed`). A job of a lane that no process
  handles waits pending.

## Global pauses

- `sqlane.lanes.pauseGlobally(lane)` / `resumeGlobally(lane)`: no runner claims the jobs of the lane, until the resume.
  The running jobs finish; the enqueues and the schedules go on, and their jobs wait pending. The resume unblocks its
  blocked jobs and sends the hint.
- `sqlane.schedules.pauseGlobally(schedule)` / `resumeGlobally(schedule)`: no runner fires the schedule. Its slots
  during the pause are skipped, with no event; the resume does not catch them up.
- Both are stored, so they hold across restarts and deploys, and work before the first deploy of a lane or schedule.
- A paused lane still counts in `lanes.stats()`: its `due` and its `oldestDueAgeMs` grow. An alert on them should skip
  the entries with `pausedGlobally: true`.

## The tables

`0010_pause` adds:

| Table                        | Change                                                                                                       |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `sqlane_paused_lanes`        | New: `lane` (primary key, the type of `sqlane_jobs.lane`) and `paused_at`. One row per globally paused lane. |
| `sqlane_schedules.paused_at` | New, nullable: the time of the global pause of the schedule.                                                 |

Update the SQL of your own, the views and the ORM models of these tables; with Prisma, list `sqlane_paused_lanes` in
its external tables ([Prisma](../adapters.md#prisma)). `schema.drop()` drops the new table too.

## Rollback

Run `schema.rollback({ targetVersion: '9.0.0' })` with 10.0, then deploy 9.x. It drops `sqlane_paused_lanes` and
`sqlane_schedules.paused_at`, and with them the global pauses: the paused lanes and schedules run again under 9.x. As
for the upgrade, stop the processes of 10.0 first.
